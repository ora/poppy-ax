### Everything happens in a session

Everything an assistant does at your company happens in a session: one person's activity, at your company, through one assistant, across your APIs, conversations and website. A session starts signed out. You know which assistant is asking and you can recognise the same person over time, but you do not know who they are ([spec 5](https://personalagentprotocol.org/docs/1.0/spec#sessions)).

There is no step to start a session and no token to hand out. The assistant names the session itself and signs every request it sends you with a `Poppy-Session` header; the first request with a new session ID starts the session. A signed-out request carries that header and no access token. Signing in, in level 3, adds an ordinary OAuth access token next to it, and stays separate ([spec 5](https://personalagentprotocol.org/docs/1.0/spec#sessions), [spec 5.4](https://personalagentprotocol.org/docs/1.0/spec#sign-in)). So this level needs no sign-in server at all.

You choose how much of this to use. An endpoint that uses nothing from the session, such as a product catalog, can answer without checking the header. To recognise a person, keep a cart, or connect a conversation with the website, you must check the header first ([spec 5.3](https://personalagentprotocol.org/docs/1.0/spec#session-verification), [guides: choosing capabilities](https://personalagentprotocol.org/docs/1.0/guides#company-adoption)).

### The assistant publishes who it is

Each assistant publishes its own metadata at an HTTPS address, and that address is its `client_id`. You fetch it to learn the assistant's name and logo, the public keys it signs with, and where sign-in may send people back ([spec 4.1](https://personalagentprotocol.org/docs/1.0/spec#agent-identity)). From the spec's example, for an assistant at `agent.example`:

<CodeLabel>Client metadata, published by the assistant</CodeLabel>

```json
{
  "client_id": "https://agent.example/agent.json",
  "client_name": "Example Agent",
  "logo_uri": "https://agent.example/logo.png",
  "jwks_uri": "https://agent.example/jwks.json",
  "redirect_uris": ["https://agent.example/oauth/callback"],
  "token_endpoint_auth_method": "private_key_jwt"
}
```

The `client_id` inside must equal the address you fetched it from. The `jwks_uri`, the assistant's list of public keys, must be an HTTPS address on the same domain as the `client_id` ([spec 4.1](https://personalagentprotocol.org/docs/1.0/spec#agent-identity)).

<details>
<summary>Details for implementers: fetching and limiting assistants</summary>

- Fetch the `client_id` address without following redirects, and cache the metadata and keys within limits ([spec 5.3](https://personalagentprotocol.org/docs/1.0/spec#session-verification), [guides: verifying personal agents](https://personalagentprotocol.org/docs/1.0/guides#company-agents)).
- You decide which assistants you accept. You may keep lists of assistants you allow or block, and limit how fast new sessions and new `client_id` values arrive. A refused assistant gets `invalid_session` at your APIs ([spec 4.1](https://personalagentprotocol.org/docs/1.0/spec#agent-identity), [guides: verifying personal agents](https://personalagentprotocol.org/docs/1.0/guides#company-agents)).

</details>

### Every request carries a Session header

On every request to your APIs, conversations and other protocol endpoints, such as your `tasks.endpoint` (level 1), the assistant sends a `Poppy-Session` header. It holds a JWT, a small piece of JSON with a signature, that the assistant signs for that one request. Next to it go `Poppy-Version`, and `Poppy-Extensions` when the assistant uses extensions with you, both explained below ([spec 5.2](https://personalagentprotocol.org/docs/1.0/spec#session-header), [spec 9](https://personalagentprotocol.org/docs/1.0/spec#task-coverage)):

<CodeLabel>Session JWT for a signed-out request, from the spec's example (header, then claims)</CodeLabel>

```json
{
  "typ": "poppy-session+jwt",
  "alg": "ES256",
  "kid": "9E421cSqd5UfAq5slDKYxXQd8Zmm8B3CIsT9cDxRHx8",
  "poppy_dlg": "eyJhbGciOiJFUzI1NiIsInR5cCI6InBvcHB5LWRlbGVnYXRpb24rand0Iiw…"
}
.
{
  "iss": "https://agent.example/agent.json",
  "aud": "https://auth.example.com",
  "sid": "Yx2b7Qd_Kp8mR3vT1nWc4A",
  "sub": "usr_Q7c1vK",
  "htm": "POST",
  "htu": "https://api.example.com/orders/ord_7Hk2/exchanges",
  "iat": 1790900000,
  "jti": "e1j3V_bKic8-LAEBq7Rw2g"
}
```

The claims, all from the spec ([spec 5.2](https://personalagentprotocol.org/docs/1.0/spec#session-header)):

- `iss` is the assistant's `client_id`.
- `aud` is your company's identifier: your issuer, or `https://` and your domain if you have none (level 1).
- `sid` is the session ID, chosen at random by the assistant and never reused.
- `sub` is a user ID the assistant makes for this person at your company. It stays the same across sessions, it is different at every company, and it is never made from personal details such as an email address ([spec 5.1](https://personalagentprotocol.org/docs/1.0/spec#user-ids)).
- `htm` and `htu` are the request's method and address, so a copied JWT works only for the same request.
- `iat` is when it was signed, and `jti` is unique.
- `ath` is a hash of the access token, present only on signed-in requests (level 3).

The JWT is not signed with a key from the assistant's `jwks_uri`. It is signed with a short-lived delegated key, and its header carries, in `poppy_dlg`, a delegation: another JWT, signed with a key from `jwks_uri`, that vouches for the delegated key for at most 24 hours. Each delegated key signs for one user ID only, so a leaked key exposes one person at one company ([spec 5.2](https://personalagentprotocol.org/docs/1.0/spec#delegated-keys)).

### Check the Session header

Before you rely on anything in the header, such as who the assistant is, which person this is, or which session or cart the request belongs to, check it in this order ([spec 5.2](https://personalagentprotocol.org/docs/1.0/spec#delegated-keys), [spec 5.3](https://personalagentprotocol.org/docs/1.0/spec#session-verification), [spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions)):

1. Fetch the client metadata from `iss`, without following redirects, and the keys from its `jwks_uri`.
2. Verify the delegation with the key its `kid` names: `typ` is `poppy-delegation+jwt`, its `iss` is the JWT's `iss`, it has not expired, and its `exp` is at most 24 hours after its `iat`.
3. Verify the Session JWT with the key in the delegation's `cnf.jwk`, and check that the JWT's `kid` is that key's thumbprint. Reject a JWT with no delegation, including one signed directly with a key from `jwks_uri`.
4. Check `typ` is `poppy-session+jwt`, `aud` is your identifier character for character, `htm` and `htu` match the request, and `iat` is recent, for example within the last minute.
5. If the request has an access token, check that `ath` matches it and that the token was issued to the same `client_id`. Without one, `ath` must be absent.
6. Look up the session by `client_id`, `sid` and user ID together. A combination you have not seen starts a signed-out session, and a known one continues its session. So a known `sid` with a different user ID names a different session; it is not an error.
7. Check `Poppy-Version`, as the next step describes.

You must accept ES256 delegations, and should accept PS384 ones too ([spec 5.2](https://personalagentprotocol.org/docs/1.0/spec#delegated-keys)). Reject `alg: none` and symmetric algorithms such as HS256 ([guides: signing and verifying JWTs](https://personalagentprotocol.org/docs/1.0/guides#both-signing)). Do not expect a person's delegated key to stay the same between requests or sessions, or treat a new one as a reason to reject a request. You may reject, with `invalid_session`, a Session JWT whose delegated key has already signed for a different user ID while a delegation for that key lasts. That limits a leaked key to one person ([spec 5.2](https://personalagentprotocol.org/docs/1.0/spec#delegated-keys), [guides: sessions](https://personalagentprotocol.org/docs/1.0/guides#company-sessions)).

If a check fails, answer HTTP 400 with `{"error": "invalid_session"}`. When a session you ended comes back, answer 400 with `{"error": "session_ended"}`, and the assistant starts a new one. These use 400, not 401, so OAuth libraries do not throw away a valid access token. A request with no header at all also gets `invalid_session` when handling it depends on the session ([spec 5.3](https://personalagentprotocol.org/docs/1.0/spec#session-verification), [spec 5.5](https://personalagentprotocol.org/docs/1.0/spec#ending-sessions)).

<details>
<summary>Details for implementers: where and how to check</summary>

The guides suggest checking the header in one place, such as a gateway in front of your APIs, your conversation endpoint and your browser join, and passing the verified `client_id`, `sid` and user ID to the services behind it. Cache verified delegations by a hash of the whole delegation until they expire, so most requests need one signature check. Behind proxies, compare `htu` with the public address the assistant used, not the `Host` header your server receives ([guides: verifying the Session header](https://personalagentprotocol.org/docs/1.0/guides#company-session-header)).

Rejecting a reused `jti` is optional. If you keep a list of seen `jti` values, share it across every server ([spec 5.3](https://personalagentprotocol.org/docs/1.0/spec#session-verification), [guides: verifying the Session header](https://personalagentprotocol.org/docs/1.0/guides#company-session-header)).

Keep a session record, which you find by `client_id`, `sid` and user ID, only as long as the session lasts. Remember the `sid` of each session you end for a while, so it gets `session_ended` instead of silently starting again ([spec 5.5](https://personalagentprotocol.org/docs/1.0/spec#ending-sessions), [guides: sessions](https://personalagentprotocol.org/docs/1.0/guides#company-sessions)).

At your APIs, conversations and other protocol endpoints, accept the header and any access token without asking for cookies, and never accept either from a URL ([spec 5.6](https://personalagentprotocol.org/docs/1.0/spec#sending-requests)). Serve each endpoint at the address you publish: if an API or protocol endpoint answers with a redirect, the assistant must not send a token, Session JWT or credentials to the new address ([spec 3](https://personalagentprotocol.org/docs/1.0/spec#discovery)).

The spec also recommends that assistants sign their requests with Web Bot Auth, so bot defenses at your edge can recognise the assistant's operator before the request reaches your application. That signature does not replace the Session header ([spec 5.3](https://personalagentprotocol.org/docs/1.0/spec#operator-signatures), [guides: operator signatures and bot defenses](https://personalagentprotocol.org/docs/1.0/guides#both-operator-signatures)).

</details>

### Check the version and extensions

A company can serve several versions of the protocol at once. Level 1 shows how `poppy.json` lists them, in `protocol_version` and `supported_versions`. The assistant chooses the newest one that it can work with, and names the version it implements in a `Poppy-Version` header on every request that carries the Session header. When it uses extensions with you, it also names them, one version of each, in a `Poppy-Extensions` header. From the spec's example ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions)):

<CodeLabel>Request headers, from the spec's example</CodeLabel>

```http
Poppy-Session: eyJ0eXAiOiJwb3BweS1zZXNzaW9uK2p3dCIs…
Poppy-Version: 1.0
Poppy-Extensions: "operations";v="3", "links";v="1"
```

- `Poppy-Version` is a version as major.minor, such as `1.0`. Two versions are compatible when they have the same major version and, before 1.0, the same minor version too.
- `Poppy-Extensions` is a list of extension names in quotes, each with the version it uses in `v`. Every name is one from the `extensions` in the file the assistant chose. A request without the header, or with one that cannot be read, declares no extensions.
- The assistant sends the same values on every request in a session. To change them, it starts a new session.

Requests without the Session header, such as fetching `poppy.json` or signing in, carry neither header ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions)).

Wherever you verify the Session header, you must check `Poppy-Version` too. If it is missing, or names a version that is not compatible with one you serve, answer HTTP 400 with `{"error": "version_unsupported"}`, and do not handle the request under some other version instead. The assistant then fetches `poppy.json` again, without a cached copy, and chooses again. If it chooses another version, it starts a new session and sends the request once more ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions)). If you serve one version, this check is all you need ([guides: serving several versions](https://personalagentprotocol.org/docs/1.0/guides#company-versions)).

Handle each request by the extensions it declares, not by anything in the assistant's client metadata, which no longer lists extensions. You may refuse a request you can handle only with an extension that the request does not declare, in a version you list, unless the request itself uses the extension. Answer HTTP 403 with `extension_required` and the extension's name in `extension`, in a JSON body ([spec 3.3](https://personalagentprotocol.org/docs/1.0/spec#extensions), [spec 4.1](https://personalagentprotocol.org/docs/1.0/spec#agent-identity)):

<CodeLabel>Response body, from the spec's example</CodeLabel>

```json
{ "error": "extension_required", "extension": "example.com/gift-wrap" }
```

<details>
<summary>Details for implementers: serving more than one version</summary>

- Accept every version you list at your endpoints, and tell them apart by `Poppy-Version`. Where a version needs its own endpoint, give that version's file its own address ([guides: serving several versions](https://personalagentprotocol.org/docs/1.0/guides#company-versions)).
- You may warn that you plan to stop serving a version with the `Deprecation` and `Sunset` headers on responses in that version ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions)). The guides suggest sending them for a while, then removing the version from `supported_versions`, then no longer accepting it ([guides: serving several versions](https://personalagentprotocol.org/docs/1.0/guides#company-versions)).
- You can offer several versions of an extension the same way, and handle each request by the version it declares ([guides: serving several versions](https://personalagentprotocol.org/docs/1.0/guides#company-versions)).
- From 1.0 on, `Poppy-Version` and `version_unsupported` keep their meaning in every version, so an assistant and a company on different major versions can always find one they share, or tell that there is none ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions)).

</details>

### Pages fetched without a browser

An assistant sometimes fetches a page of your website with its own HTTP client, not a browser, for example to read a help article. It should send the Session header with that request too, so you can tell which assistant and session it comes from. A browser, even a headless one with no screen, joins the session instead (level 4) ([spec 5.2](https://personalagentprotocol.org/docs/1.0/spec#session-header), [spec 6](https://personalagentprotocol.org/docs/1.0/spec#web-browsing)).

- It goes only to HTTPS pages whose host is exactly your `organization.domain`, the host that served `poppy.json`. Other hosts on your domain do not get it.
- It never comes with an access token, so the JWT has no `ath` and the request is always signed out, even when a browser in the same session is signed in.
- When a page redirects, the assistant signs a new Session JWT for the new address only if it is still on that host. Otherwise it follows the redirect without the header.

You do not have to check the header on these pages. If you use it, for example to recognise the assistant or keep the request in its session, verify it first, as at any endpoint. When the check fails, answer `invalid_session`, so the assistant learns its header has a mistake. It may then fetch the page again without the header. Otherwise assistants must not leave the header out to look like a person ([spec 5.2](https://personalagentprotocol.org/docs/1.0/spec#session-header), [spec 5.6](https://personalagentprotocol.org/docs/1.0/spec#sending-requests), [guides: verifying the Session header](https://personalagentprotocol.org/docs/1.0/guides#company-session-header)).

Setting `web.disabled` asks assistants not to use a browser on your website. It does not cover these requests ([spec 6](https://personalagentprotocol.org/docs/1.0/spec#web-browsing)).

### List your APIs

Now you can add `apis` to `poppy.json`. Every API you list must accept the Session header and, once you offer sign-in, your access tokens, and enforce their scopes ([spec 7](https://personalagentprotocol.org/docs/1.0/spec#apis)). Each entry has a `type`, a `url`, and a short `description` that helps the assistant pick the right API ([spec 3.1](https://personalagentprotocol.org/docs/1.0/spec#fields)):

<CodeLabel>Excerpt from poppy.json</CodeLabel>

```json
"apis": [
  {
    "type": "openapi",
    "url": "https://api.example.com/openapi.json",
    "description": "Orders, returns, and exchanges"
  },
  {
    "type": "mcp",
    "url": "https://mcp.example.com/mcp",
    "description": "Product search and sizing"
  }
]
```

The spec defines two types, and assistants skip types they do not know, so later versions can add more ([spec 7](https://personalagentprotocol.org/docs/1.0/spec#apis)):

- `openapi`: the `url` points to an OpenAPI 3.0 or 3.1 description. OpenAPI is a standard file that describes a web API's requests and responses.
- `mcp`: the `url` points to a remote MCP server using the Streamable HTTP transport and MCP version 2025-06-18 or later. MCP, the Model Context Protocol, is a common way to offer tools to AI assistants.

A language model usually reads these descriptions to choose and call your operations, so say what each one does in terms of the person's task, and keep them short ([guides: describing APIs](https://personalagentprotocol.org/docs/1.0/guides#company-api-descriptions)).

### MCP servers

An MCP server carries the Session header like any other API. One that accepts the header can take signed-out calls with it alone. One that ignores the header can still work, but its calls do not join the session's cart, conversations or website ([spec 7](https://personalagentprotocol.org/docs/1.0/spec#apis)).

When the server offers account access, it publishes protected resource metadata (RFC 9728), the same kind of file as in level 1, for its own address. Its `resource` must equal the server's `url` in `poppy.json`, and its `authorization_servers` must include your issuer. That is how MCP clients find where to get a token. A token issued for the server works only at the server whose `url` equals its `resource`, not even at other paths on the same host ([spec 4.5](https://personalagentprotocol.org/docs/1.0/spec#access-tokens), [spec 7](https://personalagentprotocol.org/docs/1.0/spec#apis)).

When a request needs a token it does not have, the server answers 401 with a challenge for each scheme it accepts, and each challenge includes `resource_metadata` with the address of that metadata ([spec 7](https://personalagentprotocol.org/docs/1.0/spec#apis)). MCP clients that do not use Poppy sign in with MCP's own flow, outside the protocol, and their requests belong to no session ([spec 7](https://personalagentprotocol.org/docs/1.0/spec#apis)).

### What your APIs answer

Access token problems follow OAuth and go in the `WWW-Authenticate` header. Session problems go in a JSON body ([spec 7](https://personalagentprotocol.org/docs/1.0/spec#apis)):

- 401 with no error code: the request needs the person's account and has no access token. Name the scopes needed in the challenge's `scope` attribute.
- `invalid_token` (401): the access token is expired, revoked or not valid.
- `insufficient_scope` (403): the access token lacks the scopes the request needs, named in `scope`.
- `invalid_session` (400, JSON body): the Session header is missing or fails a check, or you refuse this assistant.
- `session_ended` (400, JSON body): the session has ended. The assistant starts a new one and tries once more.
- `extension_required` (403): the request needs an extension the assistant does not list, named in the header's `extension` attribute.

If you limit request rates, answer HTTP 429 with a `Retry-After` header, on any endpoint ([spec 5.6](https://personalagentprotocol.org/docs/1.0/spec#sending-requests)). The guides suggest letting a signed-out session do whatever a signed-out visitor can do on your website, and limiting abuse by `client_id` rather than turning assistants away ([guides: guest access](https://personalagentprotocol.org/docs/1.0/guides#company-guest)). Keep error text free of account details and other people's data ([guides: error messages](https://personalagentprotocol.org/docs/1.0/guides#company-errors)).
