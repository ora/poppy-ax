# Moving Ora's Poppy checks to draft 1.0

A guide for Ora's team, and for the coding agents that maintain Ora's Personal Agent Protocol ("Poppy") checker, on moving its checks from Draft 0.3 to draft 1.0.

- **Where things stand (2026-11-12).** Ora's production catalog (`GET https://ora.ai/pap/catalog.json`, recorded in `fixtures/catalog.json`) is `pap-0.3@2026-11-09`, with 111 rows. It grades each file by the version it declares (0.1 to 0.3, and 0.4 as a preview). Version 0.4 was published on 2026-11-10 as the 1.0 release candidate. Draft 1.0 is 0.4 plus fixes, and it is what the spec's authors ask builders to use. poppy.ax's guide already follows draft 1.0.
- **Sources.** Every requirement cites the draft 1.0 text at `https://personalagentprotocol.org/docs/1.0/...`, read on 2026-11-12. The unversioned `/docs/spec` redirects there today. Draft 1.0 still takes fixes, so re-read the changelog's draft 1.0 section before shipping. An external research note was cross-checked for the pitfalls, test agent, probe safety and fixture sections. Its claims were checked against the 1.0 text and corrected where they were wrong.
- **What poppy.ax needs from Ora.** The API shape stays the same. Row ids stay stable, or new and retired ids are announced, because poppy.ax keeps a page per row id (`content/rows/<id>.md`) and its tests fail when the catalog and the pages disagree. When the catalog's `profile` changes, poppy.ax's weekly drift watch opens an issue.

> **Status, 2026-11-12.** Since this guide was written, Ora has moved its checks twice: first to the published Draft 0.4 (`pap-0.4@2026-11-12`), then to Draft 1.0 (`pap-1.0@2026-11-12`, 112 rows), which it follows while 1.0 is in progress. It grades 0.4 and 1.0 files by the same rules, and nothing is graded as a preview. Most of the rules below are now live: the "0.4 or later" wording, `scopes_supported` read from both metadata documents in T0-26 and T0-28, T1-03's handling of `access: signed_in`, and the new T0-34 "Signing algorithm list advertised". On versions, Ora advises a site to serve both: publish `poppy.json` as 1.0 and list a 0.4 copy in `supported_versions`; a 0.4 file is advised to move to 1.0 or list a 1.0 document. That replaces this guide's "move to 1.0" advisory. T0-29 to T0-33 are reserved for the new checks proposed here. The row-by-row review below was written against the 0.3 catalog, so check each row against the live catalog before acting on it. The planned Tier 2 and 3 rewrite is still ahead.

## Summary

Ora's Poppy checker grades Draft 0.3 today (catalog profile `pap-0.3@2026-11-09`, `spec_version` "0.3", `spec_url` `https://personalagentprotocol.org/docs/0.3/spec`). Draft 0.4 was published on 2026-11-10 as the 1.0 release candidate, and draft 1.0 is 0.4 plus fixes. Draft 1.0 says so itself: "This is draft version 1.0. It starts from 0.4, the 1.0 release candidate, and adds fixes for problems implementers find, which can include changes that aren't backward compatible" ([spec 1](https://personalagentprotocol.org/docs/1.0/spec#intro)). The changelog still lists 1.0 as "In progress" and says "This list grows until 1.0 is published" (changelog `#v1-0`). So 1.0 is still a draft, and the catalog keeps `draft: true`.

Much of the work is already done. The catalog grades many 0.3 and 0.4 features (protected_resources, scope_hints, auth.disabled, supported_versions and poppy:browser-sign-in as 0.4 previews, web.disabled and web.unscoped, the tasks endpoint, version_unsupported), and it grades each file by the version it declares. Moving to 1.0 is mostly three things: making 1.0 the version Ora grades against, turning the 0.4 "preview" logic into 1.0 rules, and adding the checks 1.0 needs that no row covers yet.

What changes:

- **The target version.** Ora grades a file declaring 1.0 by the 1.0 text. Older files are still graded by their own draft, with an advisory to move to 1.0 (see Versions). Under the compatibility rule in [spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions), a 1.0 Personal Agent does not use a 0.x document at all, so a 0.4 file no longer gets a plain pass.
- **The 0.4 preview rows become 1.0 rows.** Rows that say "Draft 0.4 (in progress, graded as a preview)" (T0-27, T0-28, and the 0.4 clauses in T0-04, T0-06, T0-08, T0-13, T0-19, T0-20, T0-23, T0-24, T0-25, T1-03, T1-05, T1-16) apply to 1.0 files and cite the 1.0 text. 0.4 is published, so no row says it is in progress.
- **New checks.** Nine new Tier 0 and Tier 1 rows and six planned Tier 2 and Tier 3 rows (see New checks), mostly from changes 0.4 made: Poppy-Version and Poppy-Extensions, the tasks endpoint, Direct Sign-In preferred, operations on websites, and the UCP extension.
- **The planned tiers.** Tier 2 and Tier 3 rows are still written for Draft 0.2. They need rewriting for 1.0 before any of them is implemented. The row tables in the other parts of this guide cover that. Every Session-based probe needs the test agent described below.
- **Catalog-wide fields.** `profile`, `spec_version`, `spec_url`, every row's `spec_url`, and the wording that names drafts (see Catalog-wide changes).

The order to do it in:

1. Build the version layer first: T0-04, the choice of which document Ora grades, and the per-version dispatch, with 1.0 as a graded version. Keep 0.1 to 0.4 grading working (see Testing and rollout).
2. Move the 0.4 preview rules to 1.0 and check each against the 1.0 text. Most carry over word for word. Check the ones 1.0 changed (the changelog's `#v1-0` list, today only the lookalike-domain note in [spec 10.3](https://personalagentprotocol.org/docs/1.0/spec#trust), which needs no check).
3. Add the new Tier 0 rows. They read only poppy.json and metadata Ora already fetches.
4. Add the new Tier 1 rows, inside the existing `tier1_policy`.
5. Rewrite the planned Tier 2 and Tier 3 rows for 1.0, still `implemented: false` and `provisional: true`.
6. Re-point every `spec_url` to `/docs/1.0/...`, set the catalog-wide fields, and update `ORA_API.md`'s examples and spec label.
7. Send poppy.ax the list of new and retired row ids before the deploy, so its `content/rows/<id>.md` pages can land in step (see Testing and rollout).
8. Deploy. poppy.ax's weekly drift watch then sees the new `profile` and opens its issue.

What done looks like:

- `GET https://ora.ai/pap/catalog.json` answers with `profile` `pap-1.0@<date>` (the day Ora last re-read draft 1.0, for example `pap-1.0@2026-11-12`), `spec_version` "1.0", `draft: true` and `spec_url` `https://personalagentprotocol.org/docs/1.0/spec`. The summary's `profile` matches.
- Every row's `spec_url` points to a `/docs/1.0/` page and an anchor that exists there (poppy.ax lists the 1.0 anchors in `tests/spec-anchors.ts` and checks its links against them). The only exceptions are rows that grade one older draft only, such as T0-21, which keep their own draft's link.
- No `pass_when` says a draft is "in progress", "a preview" or "the latest published" unless it is still true.
- A file declaring 1.0 is graded by 1.0 rules with no advisory. A file declaring 0.1 to 0.4 is graded by its own draft with an advisory to move to 1.0.
- The summary keeps its shape: the same top-level fields, the five `counts` keys, the five outcome keys, and the documented row fields. poppy.ax's parser (`lib/ora/guards.ts`) rejects a summary that drops any of them.
- poppy.ax's drift watch (`spec-watch.json`, which pins the catalog `profile`) opens its "Ora's Poppy checks moved to a new spec version" issue within a week, and poppy.ax's matching PR (new catalog fixture, row pages, draft lines, new pin) is ready to merge.

## Versions

This section covers T0-04 and the rule behind every row: which version's rules grade a file. The 1.0 text is in [spec 3.1](https://personalagentprotocol.org/docs/1.0/spec#fields) (`protocol_version`, `supported_versions`) and [spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions).

### The rules in 1.0

- `protocol_version` is required: "The protocol version the document follows, as major.minor. This draft is 1.0." ([spec 3.1](https://personalagentprotocol.org/docs/1.0/spec#fields))
- Compatibility: "Two versions are compatible when they have the same major version and, before 1.0, the same minor version. The Personal Agent chooses the newest version, among protocol_version and the versions in supported_versions, that is compatible with one it implements, and uses that version's document. If none is, it MUST NOT use any of them." ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions))
- So a 1.0 agent uses no 0.x document. 0.4 and 1.0 have different major versions. Two 0.x versions are compatible only when the minor matches too, so 0.3 and 0.4 are not compatible with each other either.
- From 1.0 on, minor versions are compatible: "From 1.0, a newer minor version won't break older Personal Agents, which use the document and ignore fields they don't recognize." ([spec 3.1](https://personalagentprotocol.org/docs/1.0/spec#fields))
- `supported_versions` maps each other version the Company serves to the URL of that version's document. Each URL "MUST be an HTTPS URL on the host that served poppy.json, after any redirects", the agent does not follow a redirect from it, and the linked document "has the protocol_version it is listed under, and no supported_versions" ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions)).
- "Every document a Company serves at the same time MUST have the same organization.domain and select the same issuer (3.2)" ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions)).
- The fields that keep their meaning: "From 1.0, the location of poppy.json and how it is fetched (section 3), protocol_version, supported_versions, Poppy-Version, and version_unsupported keep their meaning in every version, so a Personal Agent and a Company that implement different major versions can find one they share, or tell that there is none." ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions), last paragraph)

### What Ora grades

Ora acts as a 1.0 Personal Agent that also knows the older drafts. It grades each file by the version it declares, as it does today, with these rules:

| `protocol_version` | Graded by | T0-04 outcome |
| --- | --- | --- |
| `"1.0"` | Draft 1.0 | Pass, no advisory. |
| `"1.N"`, N > 0 | Draft 1.0. Fields Ora does not know are ignored, as a 1.0 agent ignores them ([spec 3.1](https://personalagentprotocol.org/docs/1.0/spec#fields)). | Pass, with a note that Ora grades 1.0 and the file's newer fields were not graded. |
| `"0.4"` | Draft 0.4, frozen at `/docs/0.4/spec`, no longer as a preview. | Pass with an advisory to move to 1.0, because a 1.0 agent will not use the file. No advisory when `supported_versions` lists a valid `"1.0"` document (T0-27 grades it), since a 1.0 agent then uses that document. |
| `"0.3"` | Draft 0.3 | Pass with the same advisory. 0.3 defines no `supported_versions`, so a 0.3 file cannot point 1.0 agents anywhere. The advisory says to publish a 1.0 document as poppy.json, and to list older documents in `supported_versions` for agents that still need them. Agents on 0.4 or later read that list. A 0.3 agent reads no `supported_versions`, so it can't use the site once poppy.json is 1.0. |
| `"0.1"`, `"0.2"` | Their own draft, as today | Pass with the same advisory. |
| Another `"0.N"` (such as `"0.5"`) | Nothing. Before 1.0, it is compatible with no version Ora implements. | Not tested, with a note naming the version. The rows that read only the fields that keep their meaning (below) are still graded. |
| `"M.N"`, M > 1 | Only the fields that keep their meaning. If `supported_versions` lists a `"1.x"` document, Ora grades that document by 1.0, as a 1.0 agent would use it. | Not tested when no 1.x document is listed. Pass when one is. |
| Missing, not a string, or not `major.minor` (such as `1`, `"1"`, `"1.0.0"`, `"v1.0"`) | Nothing | Fail (P0). An agent cannot choose a version. |

Notes on the table:

- **The advisory is an advisory, not a failure.** Today's catalog gives advisories in T0-04's note on a passing row. Keep that, so a 0.3 site does not turn `problems` overnight. The note must say why: under spec 3.4, a 1.0 agent uses no 0.x document, so to 1.0 agents the site has no usable poppy.json.
- **A 0.4 file is not a plain pass.** The external research note passes 0.4 and 1.0 files alike. That is wrong under spec 3.4, because 0.4 and 1.0 have different major versions.
- **Which document Ora grades.** Keep grading poppy.json itself by its declared version, and grade each `supported_versions` document through T0-27. The one exception is a file whose own version Ora cannot grade (a later major, or an unknown 0.N) that lists a 1.x document: grade that document, because it is the one a 1.0 agent uses. See Open questions for whether a 0.4 poppy.json that lists a 1.0 document should also have the 1.0 document fully graded.
- **Per-version endpoints.** A Company may give each version its own endpoints ([guides: Serving several versions](https://personalagentprotocol.org/docs/1.0/guides#company-versions)). Tier 1 probes go to the endpoints in the document being graded, and carry that document's version in `Poppy-Version` (see New checks, T1-18).
- **Retire the preview wording.** T0-04's text "Draft 0.4 is still in progress, so a file declaring it is graded by its rules as a preview" and "move to 0.3, the latest published one" are both out of date. 0.4 was published on 2026-11-10 (changelog `#v0-4`), and draft 1.0 now follows it.
- **Draft 1.0 can still change.** The changelog says the 1.0 list "grows until 1.0 is published" (`#v1-0`). Keep `draft: true` and re-read the changelog before each catalog release. If a later 1.0 fix is not backward compatible (spec 1 allows that), the profile date changes and the affected rows change with it.

### The fields that keep their meaning

Build these as a layer that does not depend on the declared version, so the checker handles any future file:

- Fetching poppy.json: the well-known URL, HTTPS on every hop, the last URL's path exactly `/.well-known/poppy.json` with no query ([spec 3](https://personalagentprotocol.org/docs/1.0/spec#discovery)). Rows T0-01, T0-02, T0-03 and T0-SIB.
- `protocol_version` as `major.minor` (T0-04).
- `supported_versions`: same host, no redirect, the listed version declared, no nested `supported_versions` (T0-08 and T0-27).
- `Poppy-Version` and `version_unsupported` (HTTP 400, JSON body `{"error": "version_unsupported"}`) on every request with the Session header ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions), [spec 7](https://personalagentprotocol.org/docs/1.0/spec#apis)).

Everything else, including `organization`, the issuer rules and `extensions`, is graded by the declared version. Only these fields are promised to stay stable.

### Poppy-Version on Ora's requests

- Requests with the Session header carry `Poppy-Version`, and `Poppy-Extensions` when extensions are used. "Requests without the Session header, such as discovery and OAuth requests, don't carry these headers." ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions))
- An endpoint that verifies the Session header "MUST also check Poppy-Version. It rejects a request without it, or with a version that isn't compatible with one the Company serves, with version_unsupported (HTTP 400, JSON body)". The spec sets no order between the Session check and the version check, so a request with no Session header and no `Poppy-Version` can get either `invalid_session` or `version_unsupported`. The existing rows already read the latter as not tested.
- Tier 1 probes send no Session header, because Ora has no Session yet. Proposed change: they send `Poppy-Version` equal to the graded document's version anyway. It does no harm, and an endpoint that answers `version_unsupported` to the version its own document declares is broken for every agent on that version (T1-18).
- Session probes (Tier 2) send the version as a Personal Agent would: the same value for the whole Session, and a new Session to change it ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions)).

### Row fields

- **`profile`** on every row: the new profile, including rows that grade only an older draft. They still belong to this profile.
- **`spec_url`**: point every row that grades 0.4 or 1.0 rules to `https://personalagentprotocol.org/docs/1.0/<page>#<anchor>`, using the 1.0 pages' heading anchors (the same list as poppy.ax's `tests/spec-anchors.ts`). Every anchor the implemented rows use exists on the 1.0 pages, except ADV-REDIRECT's 0.1 `guides#agent-dpop`, which stays on 0.1. The planned rows link 0.2 pages. Eight of their anchors don't exist in 1.0 (`spec#account-tokens`, `#mediated-sign-in`, `#sending-tokens`, `#sign-out`, `#starting-sessions`, and `extensions/operations#confirm`, `#operations` and `#ownership`), and five rows (T2-M4, T2-M5, T2-08, T2-25, T3-17) link the bare guides page. Others exist under the same name but now cover a different section (0.2's numbering differs), so re-map each planned row from its topic, not its anchor name. A link to a missing anchor lands at the top of the page. Keep the old draft's page only on rows that grade one older draft and nothing else: T0-21 (`/docs/0.2/`), T1-09 and T1-13 (`/docs/0.2/`), ADV-REDIRECT (`/docs/0.1/`), and T0-25 (`/docs/0.3/spec#excluded-tasks`, whose 0.3 document 0.4 replaced). The 1.0 page has an `#excluded-tasks` anchor, but it describes the tasks response.
- **`spec_ref`**: drop the "Draft 0.4" prefix (T0-27 "Draft 0.4 §3.4" becomes "§3.4", and T0-28 "Draft 0.4 §6" becomes "§6"). Keep a draft prefix only on rows tied to one old draft. Re-map the planned rows' 0.2 numbers (Pitfalls 20).
- **`implemented` and `provisional`**: keep today's rule that `provisional` is `true` exactly when `implemented` is `false`. New Tier 0 and Tier 1 rows ship with `implemented: true` and `provisional: false`. New and rewritten Tier 2 and Tier 3 rows ship with `implemented: false` and `provisional: true`. poppy.ax groups rows by `implemented` and `level` (`lib/setup.ts`), so a planned row with the wrong level lands in the wrong group on its setup page.
- **`request`**: either `null` or an object with all three strings, `method`, `target` and `condition`. poppy.ax rejects the whole catalog if one row has a partial `request`, a non-HTTPS `spec_url`, or a non-boolean `implemented` or `provisional` (`catalogRow` in `lib/ora/guards.ts`).
- **`replaces`**: set it when a 1.0 row takes over an old one, such as T2-45 for T2-38.

## Passive checks (T0, ADV, X)

Scope: the 38 rows in `fixtures/catalog.json` whose id starts with `T0-`, `ADV-` or `X-`, in catalog order. "1.0" means Draft 1.0 at `https://personalagentprotocol.org/docs/1.0/`. Its changelog lists one change after 0.4 (10.3 Lookalike domains), so every rule below that 1.0 states also holds for a file declaring 0.4. Every row keeps its id, so no poppy.ax id change is needed; rows whose `pass_when` changes need their poppy.ax content page text checked.

"spec_url only" means: point `spec_url` at the 1.0 page and anchor given, keep `spec_ref` (the section numbers are the same in 1.0), and keep `pass_when`. Files declaring 0.1 to 0.3 keep their own rules in every row unless the row says otherwise.

### Notes

1. **Which version "move to" names (T0-04).** The changelog calls 0.4 "the 1.0 release candidate" and says of 1.0: "In progress, at /docs/spec. This list grows until 1.0 is published." So the newest *published* version is 0.4, and 1.0 is still a draft. If Ora grades 1.0 while it is a draft, keep the catalog's `draft: true`, and word the advisory for 0.1 to 0.3 files as "move to 1.0 (draft)" or "move to 0.4", not "the latest published one", until 1.0 is published.
2. **Choosing among several documents (T0-04, T0-27).** 3.4 has the agent choose "the newest version, among protocol_version and the versions in supported_versions, that is compatible with one it implements". A 0.4 poppy.json can list a `1.0` document, and a `2.0` one can list `1.x`. The text does not say what a checker should do; my reading is that Ora should grade the newest document it grades (a 1.0 agent's choice) and name it in the row notes. Also, a 0.1 to 0.3 agent does not read `supported_versions` (0.3 3.1 has no such field), so a 1.0 or 0.4 file listing a `0.3` document helps only agents that implement both. The current 0.4-preview advisory "unless its supported_versions lists a 0.3 document" is Ora's choice, not a spec rule. If kept for 1.0 files, the useful version is "lists a 0.4 document", since 0.4 agents do read `supported_versions`. Label it an Ora advisory either way.
3. **Anchors.** Every anchor cited is in `anchors.json`. The 0.1 anchor `guides#agent-dpop` (ADV-REDIRECT) and 0.3 `spec#excluded-tasks` (T0-25) are not 1.0 anchors with the same meaning, so those rows keep their old `spec_url`. 1.0 `spec#excluded-tasks` exists but is now section 9.1 of the tasks response.
4. **No passive check for `tasks.endpoint`.** 1.0 9 needs a GET "with the Session header (5.2) and no access token", and "A Company MAY give different Sessions different responses". Ora can't send a Session header from Tier 0, so 0.4 and 1.0 excluded tasks, `skill_index` and `feedback.endpoint` have no Tier 0 replacement. T0-08 still checks that `tasks.endpoint` is HTTPS. A new row for the tasks response would be Tier 1 or 2, with a new id and a new poppy.ax page; that is outside this part.
5. **SHOULDs not graded.** 0.4 "Direct Sign-In preferred": "A Company that offers sign-in SHOULD offer Direct Sign-In". It could be an advisory (`authorization_code` missing from `grant_types_supported` while `urn:ietf:params:oauth:grant-type:device_code` is listed), but 1.0 4 also says the metadata "can list a grant the Company doesn't offer them", and the guides allow a Company to offer only Direct Sign-In for sensitive resources, so the list is weak evidence. Similarly Mediated Sign-In 2: its scopes "SHOULD also" be in `scopes_supported` "in its OAuth server metadata or protected resource metadata". I left both out of the verdicts.
6. **Lookalike domains (1.0 10.3).** The only change after 0.4: "Nothing in the document confirms that the domain belongs to the company in organization.name ... A lookalike domain can use another Company's name and logo and pass every check in section 3." No row changes, but poppy.ax copy for T0-01 to T0-12 and the `working` verdict should not suggest the organization's name was verified.
7. **web.unscoped description.** 1.0 6: a Company whose website gives full access "MUST describe it that way (4.7), such as \"Browse the website, and see and do anything your account can do there,\"". Whether a description says that is a judgment on free text, so I did not add it to T0-13 or T0-26.
8. **0.4 rules Ora wrote before publication.** The catalog profile is dated 2026-11-09, a day before 0.4 was published. I checked each 0.4 clause in T0-06, T0-08, T0-13, T0-20, T0-23, T0-24, T0-27 and T0-28 against the 1.0 text (0.4 plus the 10.3 change) and found them consistent, except that T0-26 and T0-28 read scopes only from the issuer's metadata, while published 0.4 and 1.0 also allow the protected resource metadata's `scopes_supported`. I did not have the frozen 0.4 page itself, only the changelog and 1.0.

## Planned checks (T2, T3)

All 62 rows are `implemented: false`, `provisional: true`, profile `pap-0.2@2026-10-19`, with `spec_url` on `/docs/0.2/` and a `pass_when` that starts "Draft 0.2 plan, being rewritten for 0.3". None of them was rewritten for 0.3, so each needs a new `pass_when`, `spec_ref`, `spec_url` and `profile` for 1.0. They fall into seven groups. Inside each group, one line per row says what it becomes; ids stay, and every retired or retitled id needs its poppy.ax page changed too.

### What every T2 and T3 row needs first

1. **Ora as a Personal Agent.** Draft 0.2 had a token endpoint that started Sessions and issued DPoP "Session Tokens". 1.0 has none of that. A Session is a `Poppy-Session` header holding a JWT that Ora signs for each request, with `typ` `poppy-session+jwt`, `alg` `ES256`, a delegated key vouched for by a delegation in `poppy_dlg`, and the claims `iss`, `aud`, `sid`, `sub`, `htm`, `htu`, `iat`, `jti` (plus `ath` with a token) (spec 5.2). Ora needs a `client_id` that is an HTTPS URL of its client metadata document, with `jwks_uri` and `redirect_uris` on the same domain (spec 4.1), and it sends `Poppy-Version` on every request with the Session header, plus `Poppy-Extensions` when it uses an extension (spec 3.4). "Ora's real client_id" in T2-M4 and T2-M5 means this document.
2. **A positive control before every negative test.** Spec 7 gives `invalid_session` for a failed check and also when "the Company refuses the client_id (4.1)", and the guides tell Companies to "Keep allowlists or blocklists of client_id values". A Company that does not accept Ora answers every request with 400 `invalid_session`, so a negative test that passes on `invalid_session` would pass falsely. Send the same request with a valid Session JWT first. If that also gets `invalid_session` (or `invalid_client` / `unauthorized_client` at the token endpoint), every row in the group reads not tested, with a reason such as "client not accepted".
3. **The right target.** Spec 5.3 lets "An endpoint that uses no Session claims ... handle a request without verifying the header", so a Session-JWT negative test only means something where verification is required: the conversation endpoint (ownership, spec 8.2) and `{browser_session_endpoint}/authorize` (spec 6). `GET {endpoint}/ora_probe/events` with a valid Session header is a good read-only control: it should answer 404 `conversation_not_found`.
4. **Who has to agree.** Signed-out rows that only read, or only create a Session record, can run with Ora's own identity. Rows that write to the company's systems (start a conversation, send a message, ask for a person, trigger an operation) must be opt-in: the verified owner asks for them, as today's level 2b. Rows that need an account need an opt-in test account from the owner, and Direct or Device Sign-In done by a person: spec 5.4 says "A Personal Agent MUST use Direct or Device Sign-In only when the User signs in themselves."

### Group 1: Sessions and agent identity (signed out)

Rows: T2-01, T2-02, T2-03, T2-04, T2-05, T2-06, T2-07, T2-08, T2-18.

What 1.0 says: "There's no separate step to start a Session: the first request with a new sid starts it" (spec 5). It "MUST reject, with invalid_session, a Session JWT without a delegation, including one signed directly with a key from jwks_uri, and a Session JWT whose delegation fails any of these checks" (spec 5.2), and a delegation's `exp` "MUST be at most 24 hours after iat". The client assertion's `aud` "MUST be the Company's issuer, as a single string", and Companies "MUST reject a client assertion with any other aud ... including their token endpoint URL" (spec 4.1). ### Group 6: Conversations

Rows: T2-26, T2-27, T2-28, T2-29, T2-30, T2-31, T2-32, T2-33, T2-34, T2-35, T2-36, T2-37, T3-13, T3-14.

What 0.2 assumed: a first message answers 201 with `conversation_id`, `status` and `responder`; messages carry their own `id`, and a reused id with other content gets `message_id_conflict` (409); reads return `conversation_id`, `events`, `cursor`, `has_more`, `status`, `responder`, and messages carry `role` and `sender`; signed out, an account question gives an authorization event with `sign_in_required`; close answers 200; handoff answers 202 with `status: queued`.

What 1.0 says (changelog items "Conversation state in four fields", "Requests are accepted, then acted on", "Request IDs on every conversation request", "Withdrawing a handoff", "Closing doesn't wait its turn", "Conversations across versions"; all Breaking except the last):
- Every POST body has a top-level `id`, and "A message's ID is its request's ID, so the message itself has no id" (8.3). A retry with the same ID, path and body returns "the original response" and isn't acted on again; a different path or body returns `request_id_conflict` (409).
- "A successful POST means the Company accepted the request, not that it has acted on it. The response has only conversation_id" (8.3): 201 for `POST {endpoint}`, 202 for messages, handoff, handoff cancel and close.
- Every read "MUST include conversation_id, events, cursor, has_more, and the state fields working, handoff, responder, and closed" (8.5). `working` is `true`/`false`, `handoff` `none`/`pending`, `responder` `agent`/`human`, `closed` `true`/`false` (8.7). Changes to `handoff`, `responder` or `closed` add a `state` event; `working` adds none. Messages carry `role` and `author.type` (8.4, 8.7).
- Streams: each event's id is its SSE id; `working` comes as `event: working` with no SSE id, and `text-delta` pieces also have none; reconnect with `Last-Event-ID`, which wins over `cursor` (8.6).
- The authorization event has `error` `insufficient_scope` "whether or not the request had an access token" and `scope` (8.11).
- `POST {endpoint}/{id}/handoff/cancel` returns 202, and the Company "MAY stop looking" (8.9). Close returns 202; afterwards messages, handoff requests and handoff cancels return `conversation_closed` (409), and "A close sent to a conversation that is already closed returns HTTP 202" (8.12).
- `version_mismatch` (409) with `protocol_version` when a conversation can't carry over to the Session's versions (8.2); it is a MAY.

### Group 7: Sign-in, scopes and account tokens

Revocation uses `token_type_hint=refresh_token` (4.6); access tokens issued under it follow RFC 7009 §2.1 (5.5). ### Group 8: Operations

Rows: T2-38, T2-39, T2-40, T3-15, T3-16.

What 0.2 assumed: Operations as declared in "Ora client metadata ... extensions.operations"; `operation_not_found` (404) for another user's operation; `terms_changed` (409) for an old revision; `standing_permission` answered by `user_approval_required` (403); a confirm step that "executes once".

What 1.0 says (Ops version 3; changelog "Operations version 3: agent approvals", "Operations require terms", "Operations: declining an approval", "Operations on websites", all Breaking): the client metadata `extensions` member "is removed" and the Personal Agent declares `Poppy-Extensions: "operations";v="3"` per request (spec 3.4, Ops 2). The approval goes in `Poppy-Approval` on the same method, target URI and content, with `operation_id`, `revision` and a required `approver` (`user` or `agent`) (Ops 6). A Session that can't approve is handled "as if it had no approval"; a revision that fails check 3 gets the operation back "with a revision for what the request asks", never "the revision it names" (Ops 6). A Company may decline: 403 `approval_declined` with `operation_id`, `revision`, optional `reason` and `alternative` (Ops 6). "The Company MUST perform each operation at most once", and while performing it answers 503 with `Retry-After` (Ops 7). The 1.0 text has no `operation_not_found`, `terms_changed`, `user_approval_required` or `standing_permission`.

- T2-39: rewrite: another User ID sending U1's approval does not get the action performed; the API answers with a new operation (403 `approval_required`); at the website `endpoint`, U1's `ref` gets 400 `invalid_request` (Ops 4). Retitle; drop `operation_not_found`.
- T2-40: rewrite: an approval of a replaced or expired revision performs nothing and returns the operation with a current revision (403 `approval_required`), never the same revision. Drop `terms_changed`.
- T3-15: rewrite end to end for version 3: `approval_required` with `terms`; resend with `Poppy-Approval` (`approver="user"`); performed once; a retry with the same approval gets the first response (Ops 7). Website variant when `endpoint` is listed: 403 with `Poppy-Operation` (`sid`, `ref`), `POST {endpoint}` with `{"ref": ...}`, 204 when the approval is recorded, then `status` `approved`, `performing`, `performed`.
- T3-16: rewrite as "An agent approval the Company won't take is declined": `approver="agent"` on an action the Company wants the person to approve gets 403 `approval_declined` with `operation_id` and `revision`, and nothing is performed. ### Notes

1. **Which check comes first, `Poppy-Version` or the Session header.** Spec 3.4 says "An endpoint that verifies the Session header (5.3) MUST also check Poppy-Version. It rejects a request without it ... with version_unsupported", but no text orders the two checks. Every T1 probe has no Session header, and 3.4 says "Requests without the Session header, such as discovery and OAuth requests, don't carry these headers", so a 1.0 endpoint that checks the version first answers T1-03, T1-16 and the new T1-09 branch with 400 `version_unsupported`, and those rows read not tested. Ora could send `Poppy-Version` with the version it grades and no Session header. Nothing in 1.0 forbids that, but nothing describes it either; if Ora does it, a `version_unsupported` answer then means the endpoint rejects the version its own document declares, which is worth a note but not a failure of these rows.
2. **`extension_required` at the token endpoint (T1-01).** The changelog ("Extensions declared per request") says "the token endpoint no longer returns extension_required", and spec 3.4 and Mediated Sign-In 2 say token requests carry no `Poppy-Extensions`. But spec 4.7 still ends its OAuth errors paragraph with "section 3.3 describes extension_required", and 3.3 allows it "at endpoints this protocol or an extension defines" without excluding the token endpoint. Hence the cautious advisory treatment in T1-01. If the editors confirm the 4.7 sentence is a leftover, the row can grade it as a fail.
3. **Same `sid`, another User ID (T2-06).** Spec 5.3: "Looks up the Session by client_id, sid, and User ID. An unknown combination starts a signed-out Session", and the changelog says "A request with a known sid and another User ID names a different Session instead of getting invalid_session, and the Company no longer checks the Agent ID". The 1.0 guides (Sessions) still say "Record the user ID and agent ID a session starts with, and reject later Session JWTs for it with different ones (5.3)". The two disagree; grade by the spec and do not fail a Company that follows the guide.
4. **Operations endpoint with no Session (T1-09).** Ops 4 says the endpoint "checks the Session header and the access token as an API does" and gives 400 `invalid_request` for "Any other reference that the Session can't use". With no Session header at all, a Company might reject an unknown `ref` before it looks at the header, which is why `invalid_request` reads not tested rather than fail.
5. **Feedback without a Session (T1-13).** Spec 9.3: "A Company SHOULD verify the Session header on a report ... The Company MUST verify the header before attributing a report ... Otherwise it can accept the report without attribution." A 202 to an unauthenticated report is therefore allowed, so there is no failure for a 1.0 T1-13 to find.
6. **Mediated Sign-In rate limits (T1-12).** Spec 5.6 says what "A Company that limits how often a Personal Agent can make requests" returns; it does not require a limit. The requirement to rate-limit is only in the guides. The extension is also marked for retirement "on a date set when version 1.0 is published", which is not set yet.
7. **DPoP error names.** `invalid_dpop_proof` and `use_dpop_nonce`, used in T2-09 to T2-16, do not appear in the 1.0 text. They are RFC 9449 names, and 1.0 leaves DPoP to that RFC ("Whether a Company binds its access tokens with DPoP is its choice, as in OAuth"). Cite RFC 9449 for them, not the Poppy spec.
8. **Where 1.0 lives.** This guide links `https://personalagentprotocol.org/docs/1.0/...`, as briefed, but the changelog says "Draft 1.0 / In progress, at /docs/spec. This list grows until 1.0 is published", and spec 1 says the draft "adds fixes for problems implementers find, which can include changes that aren't backward compatible". Check the live URL before writing `spec_url` values, and plan one more pass over these rows when 1.0 is published.
9. **Matching versions in row conditions.** Spec 3.4: "Two versions are compatible when they have the same major version and, before 1.0, the same minor version." Conditions such as "a file declaring 0.3 or later" or "a file declaring 0.4" should treat any 1.x document like 1.0. With `supported_versions`, the endpoints to probe come from the document of the version Ora grades, not always from `/.well-known/poppy.json`.
10. **People in planned rows.** Two 1.0 rules stop Ora from playing the user: spec 5.4 ("MUST use Direct or Device Sign-In only when the User signs in themselves") and spec 8.8 (`author.type` `human` "only when it carries the User's own words"). Ops 5 adds that a user approval comes from the User through the Personal Agent's own interface and an agent approval rests on the User's instruction. Every planned row that signs in, writes as the user in a Direct Conversation, or approves an operation needs a real tester on the owner's side.
11. **Severity changes this review suggests.** T2-03 (P0 to advisory: `jti` reuse is a MAY), T2-08 (Adv to P0 or P1: `alg` "MUST be ES256"), T2-09 (P0 to advisory, RFC 9449 MAY), T2-21 (P1 to advisory: 60 seconds is only in the guides), T3-11 (the Session-level part becomes advisory, the conversation part is a MUST). These are judgment calls for Ora's team.

## Pitfalls

Each item was checked against the 1.0 text. Items 1 to 12 come from the external research note's pitfalls list, corrected where the note was wrong. Items 13 on are new.

### From the external note, checked

1. **`invalid_session` has more than one meaning.** The 1.0 table says it covers "A required Session header is missing or Session verification fails (5.3), or the Company refuses the client_id (4.1)" ([spec 7](https://personalagentprotocol.org/docs/1.0/spec#apis)). For a Tier 1 probe with no Session header, it is the expected answer. For a Tier 2 probe with Ora's own valid Session, it can mean the Company has not accepted Ora's `client_id`, which spec 4.1 allows ("A Company decides which Personal Agents it accepts"). Read it as not tested in that case, not as a failure, unless the owner opted in and confirmed that Ora is accepted.
2. **Endpoints may skip Session verification.** "An endpoint that uses no Session claims MAY handle a request without verifying the header or requiring one" ([spec 5.3](https://personalagentprotocol.org/docs/1.0/spec#session-verification), and [spec 1.1](https://personalagentprotocol.org/docs/1.0/spec#layers)). A 200 answer to a request without a valid header is a failure only where the endpoint must use Session claims. Those are the conversation endpoint (ownership, [spec 8.2](https://personalagentprotocol.org/docs/1.0/spec#conversation-requests)), `{browser_session_endpoint}/authorize` ([spec 6](https://personalagentprotocol.org/docs/1.0/spec#web-browsing) step 2), the operations `endpoint` ([Operations 4](https://personalagentprotocol.org/docs/1.0/extensions/operations#approval-required)), and a tasks endpoint that varies by Session ([spec 9](https://personalagentprotocol.org/docs/1.0/spec#task-coverage)). APIs, MCP servers and a uniform tasks endpoint may skip it. T1-03 already follows this rule.
3. **A Company with no issuer is valid.** HTTP 404 or empty `authorization_servers` "means the Company has no issuer. This is valid only when auth.issuer is absent and the Company offers no sign-in" ([spec 3.2](https://personalagentprotocol.org/docs/1.0/spec#oauth-server)). The agent "MUST NOT use the domain fallback after a timeout, another error status, invalid metadata, or a failure to verify an issuer". T0-07 already fails another error status. Correction to the note: it says to fail a timeout. Ora's own convention reads a timeout, after a retry, as `not_tested` with reason `timeout`, because Ora cannot tell its own network trouble from the site's. Keep that.
4. **Domains compare exactly.** `organization.domain` "MUST be the host that serves the document, after any redirects. Domains are compared ignoring case, with no other normalization" ([spec 3.1](https://personalagentprotocol.org/docs/1.0/spec#fields)). T0-05 already does this from 0.3, and its 0.1 rule (ignoring a leading `www.`) applies to 0.1 files only. `protected_resources` is compared "as RFC 9728 §3.3 describes after lowercasing the host" ([spec 3.2](https://personalagentprotocol.org/docs/1.0/spec#oauth-server)). The note's claim about a poppy.ax issue is not used here.
5. **Old versions are outdated, not broken.** Correct, with the correction in Versions: a 0.4 file gets the same advisory as a 0.3 file, because a 1.0 agent uses neither ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions)).
6. **`grant_types_supported` does not prove a sign-in type is offered.** "Personal Agents read it from the same metadata as every other client, so it can list a grant the Company doesn't offer them" ([spec 4](https://personalagentprotocol.org/docs/1.0/spec#oauth)). This is why T0-29 is a warning, and why no row should conclude from a listed grant that sign-in works.
7. **Scopes can be missing from both lists.** "Either list MAY leave out scopes the Company offers only to its other clients" ([spec 4.7](https://personalagentprotocol.org/docs/1.0/spec#scopes)), and listing every scope an agent can request is a SHOULD ([spec 3.2](https://personalagentprotocol.org/docs/1.0/spec#oauth-server)). The note is right that a missing `poppy:browser-sign-in` is only a warning (T0-28 does this). It misses that there are two lists: see item 13.
8. **`web.disabled` binds agents, not Companies.** "The protocol can't enforce web.disabled" and it "doesn't cover pages the Personal Agent fetches without a browser" ([spec 6](https://personalagentprotocol.org/docs/1.0/spec#web-browsing)). Ora's own fetches of a site's pages don't break it.
9. **`organization.name` is not verified.** See [spec 10.3](https://personalagentprotocol.org/docs/1.0/spec#trust) and "Cannot be checked from outside". Ora's report should show the domain next to any name it quotes.
10. **poppy.json has no content-type, CORS or caching rules.** Correct: section 3 sets none, and agents cache "according to HTTP caching headers, within bounds you set" ([guides: Fetching metadata safely](https://personalagentprotocol.org/docs/1.0/guides#both-fetching)). Don't fail on them. T0-21 stays N/A from 0.3.
11. **The extensions shape changed.** The note guessed this. The changelog confirms it: "Each extension in poppy.json is a list with an entry for each version the Company supports" (`#v0-4-extensions-declared-per-request`, [spec 3.3](https://personalagentprotocol.org/docs/1.0/spec#extensions)). Correction: don't "accept both shapes with a warning". Grade by the declared version. The object shape passes in a 0.3 file and fails T0-19 in a 0.4 or 1.0 file, where an agent finds no version entries and can't use the extension.
12. **The join cookie's name.** The note says to test the cookie's properties, not its name. That is wrong for the join cookie. Spec 6 says "other hosts on the Company's domain MUST NOT be able to set it", and only the `__Host-` prefix guarantees that. The guides say the join cookie "keeps __Host- either way" ([guides: Browser sessions](https://personalagentprotocol.org/docs/1.0/guides#company-browsing)). T1-15 keeps requiring it. The note is right about the Session's cookie (step 3): its name is the Company's choice, and when the endpoint is on another host it "can't use __Host- and needs a Domain attribute" (same guide). No row should demand `__Host-` there.

### Found in the 1.0 text

13. **Scopes can be listed in two places.** A Company can list scopes "in scopes_supported of its protected resource metadata (RFC 9728 §2), instead of or as well as the issuer's metadata", and "The Personal Agent uses the scopes in either list" ([spec 3.2](https://personalagentprotocol.org/docs/1.0/spec#oauth-server), [spec 4.7](https://personalagentprotocol.org/docs/1.0/spec#scopes)). T0-26 ("every scope in the issuer's scopes_supported") and T0-28 ("the issuer's scopes_supported lists poppy:browser-sign-in") read only the issuer's list. For 0.4 and 1.0 files, read the union of both lists, so a Company on a shared issuer isn't warned for listing its scopes where the spec allows. The same applies to Mediated Sign-In's `scopes` ([Mediated Sign-In 2](https://personalagentprotocol.org/docs/1.0/extensions/mediated-sign-in#support): "in its OAuth server metadata or protected resource metadata").
14. **The token endpoint receives no `Poppy-Extensions`.** OAuth requests don't carry the version headers ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions)), and Mediated Sign-In says the agent needn't declare the extension because the token endpoint doesn't receive the header ([Mediated Sign-In 2](https://personalagentprotocol.org/docs/1.0/extensions/mediated-sign-in#support)). The changelog says "the token endpoint no longer returns extension_required" (`#v0-4-extensions-declared-per-request`). Yet [spec 4.7](https://personalagentprotocol.org/docs/1.0/spec#scopes) still says "section 3.3 describes extension_required" among the OAuth errors. T1-01 reads a 403 `extension_required` as not tested. Keep that for now and add a note for 0.4 and 1.0 files (see Open questions).
15. **`extension_required` moved out of `WWW-Authenticate`.** From 0.4 it is a JSON body at APIs too. "It isn't an access token error, so it doesn't go in WWW-Authenticate" ([spec 3.3](https://personalagentprotocol.org/docs/1.0/spec#extensions)). T1-05 already splits by version. For a 1.0 file, an `extension_required` challenge in `WWW-Authenticate` should get an advisory note, since OAuth and MCP clients may take it for a token problem.
16. **A 401 can be right at a conversation endpoint that needs an account.** T1-03 expects 400 `invalid_session`. But an entry with `access: signed_in` "requires account access before useful work can begin" ([spec 3.2](https://personalagentprotocol.org/docs/1.0/spec#oauth-server)), the 401 with no error code means "The request needs the User's account, and has no access token" ([spec 7](https://personalagentprotocol.org/docs/1.0/spec#apis)), and the spec doesn't order the account check against the Session check. For such an entry, read a 401 challenge as not tested, not as a failure.
17. **The list of endpoints that must not redirect grew.** Section 3 now names "the token, revocation, or device authorization endpoint, an API, {browser_session_endpoint}/authorize, or a conversation, tasks, feedback, or extension endpoint" ([spec 3](https://personalagentprotocol.org/docs/1.0/spec#discovery)). Add the tasks endpoint (T1-17) and the operations `endpoint` (T1-19) to T1-14. Skill artifacts are not on the list: a redirect there is allowed, under section 3's HTTPS and address rules ([spec 9.4](https://personalagentprotocol.org/docs/1.0/spec#agent-context)).
18. **Hint values a later version may add.** An agent must "treat a changes value it doesn't recognize as irreversible, so later versions can add both" ([spec 4.7](https://personalagentprotocol.org/docs/1.0/spec#scopes)). Likewise, an unknown `handoff` reads as pending and an unknown `responder` as human ([spec 8.7](https://personalagentprotocol.org/docs/1.0/spec#state)). T0-13 checks that each hint "has a changes value". For a 1.N file, an unknown value should get an advisory note (it may be a typo, or a newer version's value), not a failure. The same goes for unknown fields, API types ([spec 7](https://personalagentprotocol.org/docs/1.0/spec#apis)), conversation protocol types ([spec 8.1](https://personalagentprotocol.org/docs/1.0/spec#conversation-protocols)) and event types ([spec 8.5](https://personalagentprotocol.org/docs/1.0/spec#reading-events)).
19. **Device Sign-In links have a narrower host rule.** From 0.4, an agent shows the link only if "the link's host is the host of the Company's issuer or organization.domain (3.1), or a subdomain of either" ([spec 4.3](https://personalagentprotocol.org/docs/1.0/spec#device-sign-in)). Hosts in `protected_resources` no longer qualify (changelog `#v0-4-device-sign-in-links-on-the-issuer-or-company-domain`). Use this rule in the T3-04 rewrite.
20. **Section numbers and anchors moved.** 1.0 adds 3.4 Versions (`#versions`) and 10.8 (`#attacker-started-sign-in`). 0.3's 8.7 "Status and responder" (`#status`) is now 8.7 "State" (`#state`). The planned T2 and T3 rows cite 0.2 numbers (T2-01's "§4.2 Start a Session" is Sessions, now section 5). Re-map every `spec_ref` from the anchor, not from the old number. Drop "Draft 0.4" from `spec_ref` values such as T0-27's "Draft 0.4 §3.4", and keep a draft prefix only on rows that grade one old draft (such as T0-21's "Draft 0.2 §3.2").
21. **Duplicate JSON members.** The guides say to "reject objects with duplicate member names" ([guides: Transport and JSON](https://personalagentprotocol.org/docs/1.0/guides#both-transport)). That is advice, not a requirement, so a poppy.json with a duplicate member should get an advisory note on T0-03, not a failure. Ora's parser must detect duplicates itself, because `JSON.parse` keeps the last value without saying so.
22. **Rate limits on probes.** A Company returns 429 with `Retry-After` "on any of its endpoints, APIs, conversations, or website", and the agent "MUST wait at least that long" ([spec 5.6](https://personalagentprotocol.org/docs/1.0/spec#sending-requests)). A Tier 1 or Tier 2 probe that gets a 429 reads not tested. Ora honours `Retry-After` before any retry. T0-07's rule, which fails a rate limit on the protected resource metadata because an agent can't fall back, is a deliberate exception. Keep it.
23. **Protected resource metadata at services.** Before a signed-in call to an API or conversation endpoint, the agent fetches the service's metadata and "uses the metadata only if its resource is the URL it derived the metadata URL from ... and otherwise treats it as absent" ([spec 4.5](https://personalagentprotocol.org/docs/1.0/spec#access-tokens)). A conversation endpoint without such metadata is fine: "Otherwise the default token works there". Only MCP servers must publish it with `resource` equal to their `url` ([spec 7](https://personalagentprotocol.org/docs/1.0/spec#apis)), which T0-18 grades. Don't extend T0-18 to conversation endpoints.

## A test agent for signed-out and opt-in checks

Tier 1 probes send no Session header, so they can only check that an endpoint refuses a request it can't attribute. Every Tier 2 and Tier 3 row needs Ora to act as a real Personal Agent. This section lists what that agent needs, from the 1.0 text. It corrects the external note's section 5 where needed: the note's fields are right, but it misses User IDs per Company identifier, `Poppy-Extensions`, client assertions and the DPoP key rule.

### Identity: a client metadata document ([spec 4.1](https://personalagentprotocol.org/docs/1.0/spec#agent-identity))

- A `client_id` that "MUST be an HTTPS URL that returns its metadata document", such as `https://ora.ai/pap/agent.json`. The document's `client_id` "MUST equal the URL the document was fetched from".
- Serve it with no redirect. Companies fetch it "from iss without following redirects, as the CIMD draft (§5) requires" ([spec 5.3](https://personalagentprotocol.org/docs/1.0/spec#session-verification)).
- Members, as in the spec's example: `client_id`, `client_name`, `logo_uri`, `jwks_uri`, `redirect_uris`, `token_endpoint_auth_method: "private_key_jwt"`.
  - `jwks_uri` "MUST be an HTTPS URL on the same domain as client_id". The key set "contains only public keys".
  - Each `redirect_uris` entry "MUST be an HTTPS URL on the same domain as client_id, or a loopback redirect URI".
  - `client_name` should say plainly that this is Ora's audit agent, so an owner reading their logs knows what it is.
- 0.4 removed `extensions` from the client metadata document (changelog `#v0-4-extensions-declared-per-request`). Don't publish it.
- Keep the `client_id` stable. Companies allowlist by it: "Keep allowlists or blocklists of client_id values" and, where the authorization server needs registration, "register the personal agents you accept by their client_id URL and reject others with invalid_client" ([guides: Verifying personal agents](https://personalagentprotocol.org/docs/1.0/guides#company-agents)).

### Keys

- **Keys in `jwks_uri`** sign client assertions and delegations, never Session JWTs ([spec 5.2](https://personalagentprotocol.org/docs/1.0/spec#delegated-keys)). Use ES256, which Companies "MUST accept" for both ([spec 4.1](https://personalagentprotocol.org/docs/1.0/spec#agent-identity), spec 5.2). PS384 is only a SHOULD.
- **Blind signing** is a SHOULD "unless its own systems need to see which Companies a User works with" ([spec 10.7](https://personalagentprotocol.org/docs/1.0/spec#delegated-key-security)). Ora's audit systems need exactly that, and its Users are synthetic, so it can sign normally.
- **Delegated keys** sign Session JWTs. "The Personal Agent MUST use each delegated key, and its delegation, for one User ID only" (spec 5.2). Since a User ID is for one Company, this gives every audited Company its own delegated keys. Don't reuse a delegated key across Companies or across Ora's synthetic Users.
- **DPoP keys**, if Ora supports DPoP, as it SHOULD: "The Personal Agent MUST use each DPoP key for one User ID only" ([spec 4.5](https://personalagentprotocol.org/docs/1.0/spec#access-tokens)).
- **Rotation.** Give every `jwks_uri` key a `kid`. Publish a new key "before signing with it, early enough for companies' caches to pick it up", and keep an old one "until every client assertion and delegation signed with it has expired" ([guides: Rotating keys](https://personalagentprotocol.org/docs/1.0/guides#both-key-rotation)). The guides suggest Companies cache key sets for at most a day ([guides: Fetching metadata safely](https://personalagentprotocol.org/docs/1.0/guides#both-fetching)).

### The delegation ([spec 5.2](https://personalagentprotocol.org/docs/1.0/spec#delegated-keys))

- Header: `alg` ES256 (or PS384), `typ` `poppy-delegation+jwt`, and `kid` naming the `jwks_uri` key that signed it.
- Claims: `iss` (the `client_id`), `cnf.jwk` (the delegated public key, with no private members), `iat`, and `exp` "at most 24 hours after iat", plus a unique, unguessable `jti`.
- "The Personal Agent MUST NOT put a User ID, an Agent ID, a Company's issuer, or anything else about the User or the Companies they use in a delegation."
- Never sign a Session JWT after the delegation's `exp`.

### User IDs ([spec 5.1](https://personalagentprotocol.org/docs/1.0/spec#user-ids), [spec 3.2](https://personalagentprotocol.org/docs/1.0/spec#oauth-server))

- One User ID per synthetic User per **Company identifier**, not per domain. The identifier is the issuer, "and otherwise https://{organization.domain}, with the host in lowercase and no trailing slash". Several domains with the same issuer "are then one Company: the same User IDs (5.1), Sessions, and refresh tokens apply to all of them". So `example.com` and `example.co.uk` on one issuer see the same User ID. The external note's "one synthetic User ID per audited Company" is right only if Company means identifier.
- If a Company's identifier changes (a new issuer), "Personal Agents MUST use new User IDs, Agent IDs, and Sessions for the new identifier" (spec 3.2).
- Opaque and random. They must not be "derived from personal information". Ora's are synthetic, so this is easy.
- At least two synthetic Users per Company, U1 and U2, for the ownership rows (T2-32, T2-39 and the conversation table in [spec 8.2](https://personalagentprotocol.org/docs/1.0/spec#conversation-requests)).
- Keep the mapping of User IDs to Companies confidential ([spec 5.1](https://personalagentprotocol.org/docs/1.0/spec#user-ids)). Never show a User ID in a public report or a row note.
- Leave out `agent_id`. Ora has one agent.

### The Session JWT ([spec 5.2](https://personalagentprotocol.org/docs/1.0/spec#session-header))

- Header: `typ` `poppy-session+jwt`, `alg` `ES256` (no other value), `kid` (the delegated key's RFC 7638 thumbprint) and `poppy_dlg` (the delegation, in compact form).
- Claims: `iss` (`client_id`), `aud` (the Company identifier, as a single string), `sid`, `sub` (the User ID), `htm`, `htu` (without query or fragment), `iat` and `jti`. Add `ath` only with an access token. The agent "MUST include every claim except agent_id, and ath when there's no access token".
- Signed fresh for every request, including every retry ([guides: Retries](https://personalagentprotocol.org/docs/1.0/guides#both-retries)).
- `sid`: random, never reused, from the Conversation ID alphabet (URL-safe base64 characters, 1 to 256, [spec 8.2](https://personalagentprotocol.org/docs/1.0/spec#conversation-requests)). Use a new Session for each probe set, so one row's state doesn't leak into another's. T2-43 breaks the reuse rule on purpose and says so.
- Send it only to Session destinations: "the request URLs its listed APIs describe (section 7), and protocol endpoints listed there or derived as the protocol or extension defines". Never send it to discovery documents or OAuth endpoints. "Sharing a hostname with one of these URLs doesn't make another URL a Session destination." The one exception is website pages fetched without a browser, on exactly `organization.domain`, signed out.

### Version headers ([spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions))

- `Poppy-Version` on every request with the Session header, as `major.minor`. Choose the newest compatible version among `protocol_version` and `supported_versions`, and keep it for the whole Session.
- `Poppy-Extensions` when the probe uses an extension: an RFC 9651 List of Strings with the version in `v`, such as `"operations";v="3", "links";v="1"`. Declare "only the extensions the company lists" ([guides: Versions](https://personalagentprotocol.org/docs/1.0/guides#agent-versions)), and change it only in a new Session.
- A browser joined by Ora declares the extensions that step 2 of its join declared ([Operations 2](https://personalagentprotocol.org/docs/1.0/extensions/operations#support)).

### Client assertions, for the OAuth rows ([spec 4.1](https://personalagentprotocol.org/docs/1.0/spec#agent-identity))

- Every token, device authorization and revocation request carries a `private_key_jwt` assertion (RFC 7523) signed with a `jwks_uri` key.
- `aud` is "the Company's issuer, as a single string", never the token endpoint URL. The assertion is short-lived, with `iat` and "a unique, unguessable jti". A retried token request needs a new assertion ([guides: Retries](https://personalagentprotocol.org/docs/1.0/guides#both-retries)).

### Operator signatures ([spec 5.3](https://personalagentprotocol.org/docs/1.0/spec#operator-signatures))

- A SHOULD: sign requests that carry the Session header with an RFC 9421 HTTP Message Signature (Web Bot Auth), covering `poppy-session`, plus `authorization` when present. It helps bot defenses let Ora's probes through to the application. "Its absence does not make a Session JWT invalid", so no row depends on it.

### How the agent behaves

| Situation | What Ora does | 1.0 text |
| --- | --- | --- |
| `version_unsupported` | Fetch poppy.json again without a cached copy, and choose again. If the choice changed, start a new Session and send once more. Otherwise stop. | [spec 3.4](https://personalagentprotocol.org/docs/1.0/spec#versions) |
| `session_ended` | Start a new Session with a new `sid` and send again, once. If that also ends, stop. | [spec 5.5](https://personalagentprotocol.org/docs/1.0/spec#ending-sessions) |
| `invalid_session` | Stop. "A new Session doesn't fix it." Record it as not tested if Ora may not be accepted (Pitfalls 1). | [spec 7](https://personalagentprotocol.org/docs/1.0/spec#apis) |
| 429 | Wait at least `Retry-After`. Record the row as not tested if the wait exceeds Ora's deadline. | [spec 5.6](https://personalagentprotocol.org/docs/1.0/spec#sending-requests) |
| A redirect from a protocol endpoint | Send no token, Session JWT, assertion or credentials to the new URL. | [spec 3](https://personalagentprotocol.org/docs/1.0/spec#discovery) |
| Addresses | Never connect to loopback, private or link-local addresses from a Company's URLs. Check the address actually connected to. | spec 3, [guides: Fetching metadata safely](https://personalagentprotocol.org/docs/1.0/guides#both-fetching) |
| Tokens in URLs | Never, except in an opt-in negative test such as T2-M2, which breaks the agent rule on purpose, with a token that is revoked right after. | [spec 5.6](https://personalagentprotocol.org/docs/1.0/spec#sending-requests) |
| Conversation requests | Give each POST an `id` with at least 128 random bits, and reuse it on retries. | [spec 8.3](https://personalagentprotocol.org/docs/1.0/spec#sending-messages), [guides: Retries](https://personalagentprotocol.org/docs/1.0/guides#both-retries) |
| Browser join | Join only a browser Ora controls. Take the code only from the page that browser loaded. | [spec 6](https://personalagentprotocol.org/docs/1.0/spec#web-browsing) |
| Content from the Company | Treat it as data. If a model reads conversation replies, keep tokens, Session JWTs, keys and codes out of its context. | [spec 10.1](https://personalagentprotocol.org/docs/1.0/spec#untrusted-content), [spec 10.2](https://personalagentprotocol.org/docs/1.0/spec#secrets) |

### Sign-in

- "A Personal Agent MUST use Direct or Device Sign-In only when the User signs in themselves" ([spec 5.4](https://personalagentprotocol.org/docs/1.0/spec#sign-in)). So every signed-in row (Tier 3) needs a person, such as an Ora operator or the Company's tester, signing in to a test account that the owner provides, never a real customer's account.
- Mediated Sign-In uses "credentials the User has given it for this Company" ([Mediated Sign-In 1](https://personalagentprotocol.org/docs/1.0/extensions/mediated-sign-in#intro)). Ora uses only test-account credentials the owner supplies through the opt-in.
- Ora never sends an access token in a Session that uses an anonymous browsing User ID ([spec 5.1](https://personalagentprotocol.org/docs/1.0/spec#user-ids), [spec 5.4](https://personalagentprotocol.org/docs/1.0/spec#sign-in)).
- After a signed-in row, revoke the refresh tokens ([spec 4.6](https://personalagentprotocol.org/docs/1.0/spec#revocation)), so the test account is signed out.

### Allowlisting

A Company may refuse Ora's `client_id` entirely, or accept it signed out but refuse sign-in with `unauthorized_client` ([spec 4.1](https://personalagentprotocol.org/docs/1.0/spec#agent-identity)). The opt-in at `https://app.ora.ai/verify` should therefore tell the owner Ora's `client_id`, ask them to accept it, and record that they did. Until then, a Tier 2 `invalid_session` or `invalid_client` reads not tested.

## Probe safety

The catalog's `tier1_policy` today: "Tier 1 requests are sent only on a scan that asks for active probes, at most once per target domain every 6 hours, and never to a domain whose verified owner turned active probes off." `ORA_API.md` adds that the 6-hour round covers sibling hosts and the issuer the file names, and that a target off the domain, at a refused private address, or past a size or count limit reads `out_of_scope`. Keep all of that. The question for 1.0 is which new requests fit inside it and which need the owner's opt-in.

The rule of thumb: a request may run without opt-in only if a Company that follows the spec refuses it, or answers it without changing anything, and if a person at the Company would never see or act on it.

### The kinds of checks

| Kind | Examples | Runs | Why |
| --- | --- | --- | --- |
| Passive reads of documents agents fetch anyway | poppy.json, `supported_versions` documents, protected resource and issuer metadata, OpenAPI documents, MCP resource metadata, the UCP profile (T0-31) | Every scan (Tier 0) | Any Personal Agent fetches them before it does anything ([spec 3](https://personalagentprotocol.org/docs/1.0/spec#discovery), [UCP 3](https://personalagentprotocol.org/docs/1.0/extensions/ucp#discovery)). |
| One request with no identity, which a spec-following endpoint refuses or answers without change | T1-01 junk grant, T1-03 events read for `ora_probe`, T1-05 MCP initialize, T1-07 junk join, T1-15 join page GET, T1-16 `/authorize` with a junk code, T1-17 tasks GET, T1-19 operations lookup with a made-up `ref`, T1-20 skill artifacts | Tier 1, inside `tier1_policy` | No Session, no token, no approval. Loading the join page "MUST NOT start, end, or change any Session" ([spec 6](https://personalagentprotocol.org/docs/1.0/spec#web-browsing)). An operations request without `Poppy-Approval` records nothing ([Operations 6](https://personalagentprotocol.org/docs/1.0/extensions/operations#sending-approval)). |
| Signed-out reads with Ora's own valid Session | T2-41, T2-42, T2-43, T2-M1 | Tier 2a: on any site, once Ora runs them, inside the same window | The first request with a new `sid` starts a Session ([spec 5.3](https://personalagentprotocol.org/docs/1.0/spec#session-verification)), so these leave a Session record, but nothing a person acts on. Keep them to reads, plus `/authorize` with a junk code and operations lookups with a made-up `ref`. |
| Anything that creates state a person or system may act on | Starting a conversation (T2-26 on), handoff (T2-37, which "may page staff"), feedback reports, Mediated Sign-In attempts (T1-12), deliberate negative tests that break agent rules (replayed `jti`, tokens in a URL, wrong `aud`, reused `sid` across Users) | Tier 2b: only for a verified owner who opts in | Each one is either seen by a person, counts against an account, or imitates an attack. |
| Signed in, or performing an action | Direct and Device Sign-In, operations end to end (T3-15, T3-18), revocation, account settings | Tier 3: opt-in, a test account from the owner, and a person signing in | [spec 5.4](https://personalagentprotocol.org/docs/1.0/spec#sign-in) requires the User to sign in themselves. Actions must be sandbox ones the owner names. |

### Requests that must never run in Tier 1

- **A feedback report.** [Spec 9.3](https://personalagentprotocol.org/docs/1.0/spec#feedback): a Company that doesn't verify the header "can accept the report without attribution" and answers 202. A probe report would land in the Company's feedback queue, where people read it. T1-13 posts to a 0.2 feedback endpoint, so keep it limited to 0.2 files, and add no 1.0 equivalent outside 2b.
- **Starting a conversation**, even signed out. The Company Agent answers, and the conversation is recorded ([spec 8.3](https://personalagentprotocol.org/docs/1.0/spec#sending-messages)).
- **Starting Direct or Device Sign-In.** Even unapproved, this is "using" a sign-in type without a User signing in ([spec 5.4](https://personalagentprotocol.org/docs/1.0/spec#sign-in)). A device authorization request leaves a pending request at the issuer.
- **Junk Session headers on website pages.** Pages may verify the header ([spec 5.2](https://personalagentprotocol.org/docs/1.0/spec#session-header)), and bot defenses may block Ora's address for the rest of the scan. There is nothing to grade either.
- **Any request with `Poppy-Approval`**, and any API call other than a read-only GET.

### How the new probes fit `tier1_policy`

- **They join the existing round.** T1-17 to T1-20 are sent in the same round as the other Tier 1 rows. The round stays one per registrable domain per 6 hours, shared with the issuer, and the opt-out still stops all of them.
- **One request each, at most three artifacts.** T1-17 and T1-19 send one request each, and T1-20 at most three. T1-18 sends nothing of its own. That adds at most five requests to a round.
- **Targets off the domain.** The tasks endpoint, the operations `endpoint` and the browser-session endpoint "can be on any host the Company chooses" ([spec 6](https://personalagentprotocol.org/docs/1.0/spec#web-browsing)), and skill artifacts may be on other domains ([spec 9.4](https://personalagentprotocol.org/docs/1.0/spec#agent-context)). Keep Ora's rule: probe only targets on the scanned domain's registrable domain or the issuer's, and read the rest as `out_of_scope`. That is Ora's limit, not the site's failure.
- **Rate limits.** A 429 ends that probe for the round, and Ora honours `Retry-After` before any later request to the host ([spec 5.6](https://personalagentprotocol.org/docs/1.0/spec#sending-requests)).
- **Make the requests recognisable.** Use made-up ids that say what they are (`ora_probe`), a User-Agent that names Ora with a link explaining the probes, and an operator signature where Ora has one ([spec 5.3](https://personalagentprotocol.org/docs/1.0/spec#operator-signatures)). Send no cookies, tokens or credentials on any Tier 0 or Tier 1 fetch ([guides: Fetching metadata safely](https://personalagentprotocol.org/docs/1.0/guides#both-fetching)).
- **The policy text.** Extend `tier1_policy` by one clause, for example: "Tier 1 requests carry no Session header, access token or approval, and never start a conversation, a sign-in or a feedback report." When Tier 2a ships, describe its window in a new top-level field (such as `tier2_policy`) rather than by changing what `tier1_policy` means. `ORA_API.md` says to expect new fields, and poppy.ax ignores unknown ones.

### Keeping older-version grading working

- **Golden outcomes.** Before changing anything, record every existing fixture's summary rows under the current profile. After the change, a 0.1, 0.2 or 0.3 file's rows may differ only in T0-04's advisory text, `spec_url`, and the rows this guide changes on purpose. A 0.4 file's rows may also lose "preview". Make the test fail on any other difference.
- **Dispatch by declared version in one place.** Keep a single table from `protocol_version` to the rule set, rather than "from Draft 0.3" checks spread through each row. That is where 1.0 gets added. It also covers the clauses that today say "for a file declaring 0.4" and must now include 1.0 (Catalog-wide changes).
- **Keep the frozen texts.** Pin the 0.3 and 0.4 pages (`/docs/0.3/`, and `/docs/0.4/`, which the changelog calls frozen) next to the 1.0 pages. Each row's tests then cite the text they grade.
- **Retire no row in this release.** T0-21, T0-25, X-07, X-08, T1-09, T1-13 and ADV-REDIRECT still grade 0.1 to 0.3 files. Removing an id needs a poppy.ax change in step (below), and the files they grade still exist.

### Rolling out without breaking poppy.ax

**Keep the API shape stable.** poppy.ax's parser (`lib/ora/guards.ts`) rejects the whole summary if any of these is missing or mistyped:

- the summary's `domain`, `profile`, `last_run`, `verdict`, `counts`, `rows`, `probed_at` (string or null) and an https `report_url`;
- all five `counts` keys (`tier0`, `tier1`, `tier2a`, `tier2b`, `tier3`), each with all five outcome keys;
- each row's `id`, numeric `tier`, `level`, `severity`, `outcome`, and `reason` and `note` as string or null.

It rejects the whole catalog if any row lacks a documented field. New rows only add entries. Don't add an outcome value: a warning is a note on a row, as today. Avoid new `reason` values unless they are announced. poppy.ax shows unknown reasons as generic "not measured" text, which works but explains nothing.

**Change the profile in one deploy.** The checker and the catalog move together, so every new summary carries `pap-1.0@<date>` and the 1.0 row set. Results stored from before the deploy keep the old profile until the domain is scanned again. The summary returns the latest stored result, however old. Stored Tier 1 rounds (up to 30 days) have no result for T1-17 to T1-20. Those rows read `not_tested` with reason `null` until the domain's next probe round, which is the existing behaviour for a missing round.

**Announce the row ids first.** About a week before the deploy, send poppy.ax the new catalog, ideally served from a staging Ora, so it can be recorded as `fixtures/catalog.json`. With it, send the list of ids:

| Change | Ids |
| --- | --- |
| New, implemented | T0-29, T0-30, T0-31, T0-32, T0-33, T1-17, T1-18, T1-19, T1-20 |
| New, planned | T2-41, T2-42, T2-43, T2-44, T2-45, T3-18, plus any the row-table parts add |
| Replaced | T2-38 by T2-45 (`replaces`) |
| Retired | None |
| Renamed or re-levelled | Whatever the row-table parts decide for the T2 and T3 rewrites |

poppy.ax's tests fail if a catalog row has no `content/rows/<id>.md` page or a page has no row (`tests/rows.test.ts`). They also check that each page's `spec_section` equals the row's `spec_url`, and that `spec-watch.json`'s pin equals the recorded catalog's `profile` (`tests/spec-version.test.ts`). So poppy.ax's PR carries the new fixture, a page for each new id, the updated `spec_section` of each moved row, the checker draft lines, and the new pin, all together. It merges right after Ora's deploy.

**What poppy.ax sees at each step.**

1. *Before the deploy:* nothing changes.
2. *After the deploy, before poppy.ax's PR:* live summaries carry ids that poppy.ax's recorded catalog doesn't know. Its row loader falls back to the catalog title or the id, and it counts an unknown Tier 0 or Tier 1 row as one that runs today (`lib/verdict.ts`). The site keeps working, with plainer text for the new rows.
3. *The weekly drift watch:* it sees the live `profile` differ from the pin and opens its issue, "Ora's Poppy checks moved to a new spec version - update poppy.ax".
4. *After poppy.ax's PR:* the pin matches the live value, and the next weekly run closes the issue.

**Rollback.** If the deploy is rolled back, the profile goes back to `pap-0.3@2026-11-09`, the drift watch opens its issue again, and poppy.ax reverts its PR. Keep the 0.3 catalog build deployable until 1.0 has run cleanly for a week.

## Open questions

1. **A 0.4 poppy.json that lists a 1.0 document.** A 1.0 agent uses the linked document. Should Ora grade that document with every Tier 0 row, or only check it for consistency through T0-27, as proposed? Full grading is what agents see. Partial grading keeps one graded document per site.
2. **A visible version advisory.** The "move to 1.0" advisory is a note on a passing T0-04, so poppy.ax counts the site as passing and shows no advisory unless it reads notes. Should it be its own `Adv` row (a new id, such as ADV-VERSION), so it shows as a row?
3. **How a warning is reported.** P2 rows "warn and never fail" (T0-26, T0-28, and now T0-29), but the summary has no warning outcome. Today a warning is a pass with a note. Should a SHOULD gap be `fail` at P2 instead? It wouldn't change the verdict, which only P0 and P1 failures move.
4. **`extension_required` at the token endpoint.** The changelog says the token endpoint no longer returns it, and the token endpoint receives no `Poppy-Extensions` (Mediated Sign-In 2). But spec 4.7 still points to section 3.3 for it among the OAuth errors. Is a 403 `extension_required` from a 1.0 token endpoint a defect? Ask the spec authors. Until then, T1-01 reads it as not tested.
5. **`Poppy-Version` on Tier 1 probes.** Spec 3.4 says requests without the Session header "don't carry these headers". T1-18 relies on Ora sending `Poppy-Version` anyway, with no Session header, and failing a `version_unsupported` answer to a served version. Confirm that this reading is fair, or limit T1-18 to Tier 2a (T2-41).
6. **UCP.** Which `scopes_supported` list satisfies "MUST list each scope in its identity linking config.scopes in scopes_supported, as UCP requires": the issuer's, the protected resource metadata's, or either? Will Ora parse UCP profiles (capabilities, identity linking), whose format UCP defines? And do the 0.3 and 0.4 UCP pages say the same, so T0-31 and T0-32 can cover those files?
7. **The canonical 1.0 URL.** The changelog says draft 1.0 is "In progress, at /docs/spec". The catalog will use `/docs/1.0/spec`. Is `/docs/1.0/spec` stable while 1.0 changes, and does it stay after publication? `ORA_API.md`'s "frozen page" wording needs a new definition either way.
8. **The profile date while 1.0 changes.** Does every new 1.0 changelog entry that changes a rule move the profile date? That opens a poppy.ax drift issue each time. Or does Ora move it only at set points?
9. **Numbering with the row-table parts.** T2-41 to T2-45 and T3-18 assume the other parts add no T2 or T3 ids first. Agree on one list before release.
10. **Tier 2a without opt-in.** Once Ora runs Tier 2a, will it run on every site with a poppy.json, as the "soon" grouping suggests, or only on sites that accept Ora's `client_id`? T2-43 reuses a `sid` across two synthetic Users on purpose. Is that acceptable in 2a, or should it move to 2b?
11. **Device Sign-In link host.** Reading `verification_uri` needs a device authorization request, which spec 5.4 allows only when a User signs in. Confirm that this check stays in Tier 3 (T3-04), with a person signing in.
12. **Off-domain targets.** The tasks endpoint, the operations `endpoint`, the browser-session endpoint and skill artifacts may be on any host. Should Ora keep reading targets outside the scanned registrable domain and the issuer's as `out_of_scope`, or allow a provider's host named in poppy.json?
13. **Old drafts.** How long does Ora keep grading 0.1 and 0.2 files? Under spec 3.4 they are as unusable to 1.0 agents as 0.3 files. A sunset date would let rows such as T0-21, X-07, X-08 and ADV-REDIRECT retire in a later release, with a poppy.ax change in step.
14. **`T0-04` for a later 0.N.** Should a `"0.5"` file, which no current draft defines, read not tested (as proposed) or fail? Before 1.0, no agent can use it.
